## 一、项目与需求

### 1.1 项目目标

DormMate Final 是一个**多节点宿舍环境助手**。它把宿舍的温湿度采集上来，经 MQTT
推到浏览器，实时显示成一块看板；人在看板上点一下「开始处理」，系统记下这笔动作，
再由**后续收到的数据**判定问题到底好没好；同一份数据同时落一份档案，交给 Python
侧做规则复核、状态统计、趋势图和 HTML 报告。

一句话概括它的技术目标：**把「判断」收拢到一个地方，让所有前端只负责画。**

整条闭环是 **采集 → 展示 → 导出 → 分析** 四段。前端是纯静态的（不需要构建、
不需要打包工具），后端只有本机一个 Mosquitto Broker，**没有服务器程序、没有数据库**。

### 1.2 使用场景

| 场景 | 谁在用 | 系统提供什么 |
|---|---|---|
| **日常监看** | 值班的人，看着墙上大屏 | 三间宿舍三张状态卡 + 优先关注；温度湿度与状态徽章实时刷新 |
| **出现异常** | 值班的人 | 自动开一条事件；点「开始处理」记下动作；处理之后由数据判「已恢复 / 未恢复」 |
| **人不在电脑前** | 手上不空、戴着手套的人 | 移动端 H5：谁该管、点一下看他、按开始处理；语音说「朗读」把当前状况念出来；说「拍照」留下现场 |
| **想知道空间关系** | 需要一眼看出「哪个房间要关注」 | 3D 页面：三间房并排，谁异常谁的地板/窗/风扇变样，重点那一间浮一圈脉冲光环 |
| **事后复盘** | 要写报告、要做统计的人 | 单文件 HTML 报告：每个宿舍的极值与均值、趋势图、事件时间线、今日摘要、Rule-ML 对照 |
| **故障演练** | 验收、答辩现场 | 一条命令把九种坏消息发全，并当场核对 core 有没有真的拦住、拒的理由对不对 |

### 1.3 八个核心业务问题

> 这八条是从**代码里真实存在的行为**反推出来的，映射到具体模块与页面上。
> 仓库里没有任务书文件，所以措辞是按实现反推的，不是题面原文。

| # | 问题 | 谁回答 | 在哪儿看得见 |
|---|---|---|---|
| 1 | 这三个宿舍现在各是什么状况？ | `status_rules.py` 算出 `status`；`core.py` 写进快照 | 三张状态卡 + 状态徽章；快照 `nodes[].status` |
| 2 | 现在最该先看哪个宿舍？ | `rules.rank_priority()` 四步排序，每步带一句人话理由 | 看板顶部「当前重点」、3D 脉冲光环、语音提醒念的那句 |
| 3 | 到底多严重、已经持续多久了？ | `core.py` 维护「连续异常段」，时长取自**报文里的 `time`** | 卡片上的时长、`priority.reason` |
| 4 | 出了问题怎么处理，处理完好了没有？ | `events.py` 事件状态机 | 「开始处理」按钮、事件表、`data/events.json` |
| 5 | 页面上的数字可信吗？我看的是哪一版？ | core 是唯一业务大脑；快照带版本号 `v` | `logic.js` 里没有阈值（有测试盯着）；`v` 对不上的快照前端一律拦下 |
| 6 | 数据断了、节点失联了，知不知道？ | 离线检测（30 秒无遥测）+ core 心跳（5 秒一帧） | 卡片上「已离线 3 分钟」、三个页面各一条 core 心跳提示 |
| 7 | 这一天到底发生了什么？ | `history.py` 逐条落盘 + `make_report.py` 出单文件报告 | `report/history-report.html` |
| 8 | 规则说正常，模型也说正常吗？ | `analysis/ml.py`（离线）与 `ml_judge.py`（在线）各跑一次 Isolation Forest | 看板「实时 Rule-ML 对照」表、报告「Rule-ML 对比」+「案例分析」 |

另有两件不算业务问题、但必须交代的事：

- **多端一致**：看板、移动端、3D 三个页面订的是**同一条** `dormmate/v1/state`，
  判断用的是**同一份代码**（`dashboard/logic.js`）。移动端和 3D 点一下会发 `focus`，
  core 记进快照，另外两端跟着切过去 —— 这就是「跨端焦点」。
- **处理动作那条红线**：点上按钮**不能直接把事件置成「已恢复」**（详见 3.5）。

## 二、系统架构与两条数据链

### 2.1 四个进程 + 一个 Broker

全系统只有四个进程加一个 Broker，**没有服务器程序、没有数据库、没有构建工具**：

```
┌──────────────────── 实时链（单向：数据往上走）────────────────────┐
│                                                                  │
 simulator/                    mosquitto                 core.py   │
 publish_one.py  ──publish──▶  TCP 1883  ──订阅通配符──▶ 校验 → 判状态 │
 剧本回放                      retained                 → 存历史     │
                                                        → 算优先关注 │
                                                        → 事件状态机 │
                                                        → ML 判断    │
                                                             │       │
                                                  publish（retained）│
                                                             ▼       │
                                              dormmate/v1/state      │
                                                             │       │
                                      WebSocket 9001（浏览器唯一入口）│
                              ┌──────────┬────────────┬──────────┐   │
                              ▼          ▼            ▼          ▼   │
                         dashboard/   mobile/      three/      web/  │
└──────────────────────────────────────────────────────────────────┘

┌──────────────── 指令链（反向：人 → core）─────────────┐
 前端按钮 / send_cmd.py / 剧本 handle 帧 ──▶ dormmate/v1/cmd
                                              │
                              core 校验 → events.apply_action()
                              （只推成 HANDLING，**不判恢复**）

┌──────────────── 离线链 / 档案链（事后：档案 → 报告）──────────────┐
 core.py ──追加一行──▶ data/history.csv ─┐
 core.py ──落盘────▶ data/events.json  ─┤─▶ analysis/make_report.py ─▶ 单文件 HTML
                                         └─▶ analysis/train_iforest.py ─▶ models/*.joblib
```

**关于「两条链」的说法**：任务书里说「两条数据链」，指的通常是**实时链**（数据往上走）
与**离线链**（档案变报告）。本实现里这两条都在，另外**多出一条反向的指令链** ——
人往前端按一下，指令要回到 core 去。它不能并进实时链，因为方向相反、而且
**retained 语义相反**（遥测和快照要 retained，指令绝不能 retained）。所以下文按三条讲。

### 2.2 Topic 与数据流

| Topic | 谁发 | retained | QoS | 说明 |
|---|---|---|---|---|
| `dormmate/v1/nodes/<nodeId>/telemetry` | 发布端（模拟器 / `publish_one` / 剧本） | **是** | 1 | 一条读数 |
| `dormmate/v1/nodes/+/telemetry` | —— | —— | —— | **订阅用**（core 订这条；`web/` 也订） |
| `dormmate/v1/state` | core | **是** | 1 | 全局状态快照。**看板 / 移动端 / 3D 只订这一条** |
| `dormmate/v1/cmd` | 前端 / `send_cmd.py` / 剧本 | **否** | 1 | 指令 |
| `dormmate/v1/log/reject` | core | **否** | 1 | 非法报文（清 retained 的那条空报文不算） |
| `dormmate/v1/core/status` | core | **是** | 1 | core 在线 / 离线（遗嘱 LWT） |

两条容易踩的设计约束：

- **`cmd` 不 retained**。指令是一次性的，留在 Broker 上会让下一次起 core 时
  **凭空**把某条事件推进「处理中」。
- **`log/reject` 不 retained**。坏消息不许留在 Broker 上，否则每开一个看板都先看到它。

topic 字符串**只有 `config.py` 一处出处**。前端那份常量在 `shared/config.js`，
由一条**双向核对**测试盯着：`config.py` 里每个 topic 字面量必须在 `config.js` 里
有同名常量，反之亦然 —— 少一个方向就等于允许两边各写各的。

### 2.3 实时链

发布端每轮给每个选中节点各发一条遥测到 `dormmate/v1/nodes/<nodeId>/telemetry`，
**retained + QoS 1**。core 订阅通配符，收到后依次做五件事：

1. **校验**（九道判据）：形状、类型、`time` 格式、节点是否已知、
   **topic 里的 nodeId 与报文里的是否一致**。不合法 → 发到 `log/reject`，不写档案。
2. **判状态**：按统一规则由温湿度算出 `status`。报文里带的 `status` 对不上只记一笔
   `statusMismatch`，**不拒收** —— 数据本身没错，丢掉反而少一条读数。
3. **存历史**：追加一行到 `data/history.csv`；内存里按节点保留最近 `historyMax` 条。
4. **算优先关注**：四步排序（时长 → 条数 → 严重度 → 字典序），每一步带一句人话理由。
5. **事件状态机 + ML 判断**，然后把全局快照 retained 发到 `dormmate/v1/state`。

浏览器侧唯一的入口是 **WebSocket 9001**。三个新页面只订快照这一条，
订阅到之后**原样渲染**：`status` 是 core 算好的结论，页面不修不补不复核。

### 2.4 指令链

人按住前端按钮 → 发一条指令到 `dormmate/v1/cmd`（**不 retained**）→ core 校验
→ 交给 `events.apply_action()`。

这条链上最要紧的设计是**它改不动业务结论**：

- `handle` 只能把事件从 `OPEN` 推到 `HANDLING`，**推不到 `RECOVERED`**；
- `handle_command()` 的函数体里**一次都不出现 `self.nodes`** —— 它拿不到节点状态，
  就算想顺手把节点标成「正常」也无从下手；
- `focus` 只改 `self.focus` 那三个字段（谁、谁发的、什么时候），
  **不动任何节点、不动任何事件**，也不能凭空开案。

「处理中」是**事件**的状态，不是节点的状态。节点那边只有「这一段现在是不是异常」，
从来没有多过「处理中」这一档。

### 2.5 离线链（档案链）

`core.py` 是这条链的生产者，只追加、从不改：

- **`data/history.csv`** —— 每收到一条**合法**遥测追加一行，十列。
  它是**档案**：一条读数一行，没有轮转、没有上限，一条都不许丢。
- **`data/events.json`** —— 事件的完整记录（见 3.4）。

消费者是 `analysis/`：

| 脚本 | 读什么 | 出什么 |
|---|---|---|
| `make_report.py` | `history.csv` + `events.json` | **单文件** HTML 报告（趋势图 base64 内嵌，无外部依赖） |
| `train_iforest.py` | `history.csv` | `models/<nodeId>.joblib` + `models/MANIFEST.json` |
| `ml.py` / `analysis.py` | 历史 CSV + 待判断新数据 | 命令行对照表 + `report/ml_result.json` |

**报告是数据的纯函数**：换一份 `--csv`，整篇跟着变，没有一个数字是手写的。
这是「报告结果禁止手工修改」这条规矩的技术落点 —— 要改就改输入再重跑。

## 三、核心数据结构

### 3.1 遥测报文 telemetry

发到 `dormmate/v1/nodes/<nodeId>/telemetry`：

```json
{"nodeId":"dorm-a","temperature":31,"humidity":78,"status":"偏热",
 "time":"2026-09-22 20:30:00","seq":1,"source":"sim"}
```

| 字段 | 约定 |
|---|---|
| `nodeId` | 必须与 topic 里的那一段一致，否则拒收 |
| `temperature` / `humidity` | 数值。**core 不做范围校验** —— 99℃ / 200% 会被如实收下（见 6.2） |
| `status` | **永远由温湿度算出**，没有任何参数能手工塞一个进去 |
| `time` | 固定 `YYYY-MM-DD HH:mm:ss`。剧本里可以写死，于是「持续了多久」是可复现的 |
| `seq` / `source` | 可选。`seq` 是发送序号；`source` 是来源标记（`sim` / `manual` / `script` / `constructed`），报告的数据来源分类读的就是它 |

**统一的状态判定规则**（按顺序判断，命中即停 —— **顺序不可调换**）：

| 顺序 | 条件 | `status` |
|---|---|---|
| 1 | `temperature < 18` | 偏冷 |
| 2 | 否则 `temperature >= 30` | 偏热 |
| 3 | 否则 `humidity >= 75` | 偏湿 |
| 4 | 其余 | 正常 |

所以 **31℃ / 80% 是「偏热」而不是「偏湿」** —— 规则 2 先命中。四条回归数据
（`25/60→正常`、`16/60→偏冷`、`31/60→偏热`、`25/80→偏湿`）在 Python 侧与 JS 侧
都被钉死。

### 3.2 状态快照 state

core 发到 `dormmate/v1/state`，retained。下面是**从跑着的系统里真抓下来的**一帧
（为篇幅只留一条 `history`）：

```json
{
  "v": 2,
  "time": "2026-09-30 19:42:16",
  "core": { "online": true, "epochMs": 1790768536610, "staleAfterSec": 15 },
  "focus": { "nodeId": "dorm-c", "by": "3d", "at": "2026-09-30 19:35:33" },
  "priority": {
    "nodeId": "dorm-c", "status": "偏冷", "severity": 1,
    "abnormalCount": 93, "durationSec": 488.0, "durationText": "8 分钟",
    "reason": "已连续偏冷 8 分钟（93 次），持续时间和 dorm-a 一样长，异常次数最多"
  },
  "nodes": [{
    "nodeId": "dorm-a", "online": true, "status": "偏湿",
    "temperature": 25.0, "humidity": 80.0, "time": "2026-09-30 19:42:16",
    "mlLabel": "normal", "mlText": "接近历史常态", "agree": false,
    "abnormalCount": 92, "durationSec": 488.0, "durationText": "8 分钟",
    "reason": "也偏湿，持续时间和它一样长，但只有 92 条异常数据",
    "lastSeen": "2026-09-30 19:42:16",
    "offlineSec": null, "offlineText": null, "historyCount": 50,
    "history": [
      { "time": "2026-09-30 19:39:00", "temperature": 25.0, "humidity": 60.0,
        "status": "正常", "mlLabel": "normal", "mlText": "接近历史常态", "agree": true }
    ]
  }],
  "events": { "summary": { "total": 51 }, "events": [] },
  "rejects": { "total": 0, "kept": 0, "items": [] }
}
```

几个字段的**读法**（每一条都对应 1.3 里的某个业务问题）：

| 字段 | 意思 | 注意 |
|---|---|---|
| `v` | 快照版本，**必须是 2** | 前端 `readSnapshot()` 只放行 `v === 2`，对不上的整帧拦下不画 |
| `core.epochMs` + `core.staleAfterSec` | 这一帧的生成时刻 + 「多久算旧」（core 算好放进来） | 三个前端**不各自写一遍这个阈值**；`staleAfterSec` 为 `null` 时页面说「判不了」，**不猜** |
| `core.online` | 恒为 `true` | ⚠ **不能拿它判 core 死活** —— 它由 core 自己写，core 死了之后 Broker 手里那份 retained 快照**还带着 `true`**。判死活只有「这一帧有多旧」这一条路 |
| `nodes[].online` / `offlineSec` / `offlineText` | 节点在不在线、离线多久 | `online` 是**算出来的**（`now - lastSeen > offlineTimeoutSec`），不存成标志位 |
| `nodes[].mlLabel` / `mlText` / `agree` | core 在线的 ML 判断 | 没模型 / 没装 sklearn / 这条在 core 启动之前 → `null`（**不是 `false`**）。写成 `false` 的话，前端那个 `agree === false` 会把每一行都标成「两边不一致」，整列反过来 |
| `priority` | 谁最该先看 | 三个都正常时是 `null`（不是空对象） |
| `events.summary.total` vs `events.events` | 真总数 vs 只留最近 20 条 | 两个数**混不得**：环形缓冲一满，看板上「共 N 条」会跟着数组一起封顶 |
| `rejects.items[].payload` | 被拒的原文 | 和真发出去的那条**一个字节都不差**（前端要把原文摆出来给人看） |
| `focus` | 跨端焦点（谁、哪个动作发的、什么时候） | **不落盘** —— 它是「现在在看哪个」，不是历史；core 重启后是 `null` |

### 3.3 指令 cmd

发到 `dormmate/v1/cmd`，**不 retained**：

```json
{"nodeId":"dorm-b","action":"handle","source":"dashboard","time":"2026-09-30 19:42:16"}
{"nodeId":"dorm-c","action":"focus","source":"mobile"}
```

- `action` 目前有三个词：`handle`（开始处理）、`focus`（跨端切焦点）、
  `snapshot`（**碰得到案卷、但一个状态都不动**的动词，语音/拍照那条路在用）。
- `action` **不做大小写归一**：`Handle` 不认，理由里明说了要小写 ——
  悄悄认下的话，前端写错了永远没人发现。
- `focus` 不带 `time`（它是一个动作，不是一条读数）。
- `handle` 的 `time` 用的是**快照里那个节点的最新时刻**，不是按按钮那一刻 ——
  三台机器的钟不一定对得上，所以用数据自己的时刻。
- 五种来源：看板按钮（`dashboard`）、移动端（`mobile`）、3D 页面（`3d`）、
  `send_cmd.py`（`manual`）、剧本帧（`script`）。core 那行 `[指令]` 括号里就是它。

### 3.4 事件 events.json

`data/events.json` 由 `events.py` 读写，写 `<名>.tmp` 再 `os.replace` 原子换上去。
一条事件里值钱的是四样：

| 字段 | 是什么 |
|---|---|
| `verify` | 处理之后收到的那些数据，**一条不落地记着**（这是「好了几条」的唯一凭证） |
| `verify_from` | **下标**：「从第几条验证数据之后开始算」 |
| `snapshots` | 开案 / 处理 / 结案三个时刻的现场 |
| `result` | 最后那句人话 |

外加 `actions`（那笔处理动作的流水）、`start_time`、`recovered_at`、`state`、`priority` 等。

**落盘时机**：开案 / 转处理中 / 结案这三个时刻**立刻**写（状态迁移丢了就说不清
发生了什么）；验证数据一条一条**攒着**写，同一秒内只落一次盘 ——
一条迟迟结不了案的事件，中途收到的验证数据也都在文件里，core 被杀掉也不会把
「处理之后收了几条」丢掉。

**启动时 `load()`**：文件读不动 → 改名成 `events.json.bad` 再继续（**不覆盖**，
那份是查问题的线索）；某几条坏了 → 跳过并报数，不因为一条坏的就丢掉整本；
**读到还没结案的事件，一律按 `UNRESOLVED` 收尾**，`result` 里写明是重启造成的 ——
不然它会永远挂在「处理中」，重启一次变一次。

> `data/events.json` **不入库**：每次跑都在变，入库会让每次演示都多一个「改动」。

### 3.5 事件状态机

```
   异常数据来               收到 handle 指令            后面连着 N 条正常
 ─────────────────► OPEN ──────────────────────► HANDLING ──────────────► RECOVERED
                    │                             │
                    │                             └── 后面连着 N 条还是异常 ──► UNRESOLVED
                    └──（这条事件已经开着，段里的后续异常不再另开）
```

四个状态、四条转移。两个门槛数默认都是 3，但**在 `core/config.json` 里不在同一层**：
`recoverConsecutiveNormal` 是**顶层**键，`verifyConsecutiveAbnormal` 在 `events` 块里
（`README.md` 第 `:284` 行那张配置表也是这么标的）。位置不齐是历史原因，
两个数都在配置文件里、**事件层不自己定门槛**这一条不变。

**四条红线落在哪一行** —— 红线不能靠「记得别这么写」，得靠**结构上做不到**。
所以每一条都在源码里有个具体位置，并由一组拿 `ast` 抠出函数体的静态检查钉住：

| 红线 | 落在哪 | 测试怎么盯 |
|---|---|---|
| 处理指令不能把事件改成 `RECOVERED` | `apply_action()` 里对 `event.state` 只有一处赋值，而且是 `= HANDLING` | 抠出函数体，把所有对 `event.state` 的赋值列出来，必须正好是 `['event.state = HANDLING']` |
| 恢复只能由后来的数据判定 | `event.state = RECOVERED` 这个字符串**只出现在 `_close_recovered()` 里** | 全文件搜这个字符串：除它之外一处都不许有 |
| `_close_recovered` 不是谁都能叫 | 它只被 `observe()` 调用 | 搜调用点，必须只有一处 |
| core 不越权改节点状态 | `Core.handle_command()` 里**一行都不碰 `self.nodes`** | 抠出函数体，`self.nodes` 一次都不许出现 |

第四条是最要紧的：`handle_command` 拿不到 `NodeState`，**「处理中」不是节点的一个
状态，是事件的一个状态**。两套状态混成一套的话，「处理中」会被当成一种环境状况
去和「偏湿」比严重度 —— 那是两个维度的事。

**两处容易想岔的地方**（都是实测踩出来的）：

- **判据不能数存档里的条数。** 一开始 `UNRESOLVED` 是看 `verify` 数组最后 3 条
  是不是都异常。这默认了「存档上限 ≥ 门槛」，而这两个数是分开配的 ——
  配成 `eventsVerifyMax=2` / 门槛 3 时，第 3 条异常早被挤掉，于是怎么喂都判不出
  未恢复，连「丢过东西」这个线索都没有。现在事件上挂了个运行期的
  `pending_abnormal` 计数，**存档留多少条不参与判定**。
- **`verify_from` 记的是下标，不是条数。** 在已经 `HANDLING` 的事件上再点一次
  `handle`，只多记一笔 `actions`，**不动 `verify_from`** —— 动了的话第二次点击会把
  验证窗口往后推，前面已经收到的正常数据就白算了。**连点很多次也不重置窗口**：
  重置的话连点几下就能把「连续 M 条依旧异常」那条判据一直往后推，
  事件永远判不出未恢复，验证环节等于白设。

## 四、D1–D5、E1–E3 关键实现思路

> 本节只写**设计思路**，不贴大段代码。要动手就照 `README.md` 第 7 节
> 「D1–D5 快速复现指引」那一节走。

### D1 —— 基础链路

**目标**：一条数据从发布端走到看板上，四个状态都出现过。

**思路**：链路本身没有算法，价值在**证明它真的通了**。合格线卡在三件事上：

1. 四个状态（正常 / 偏冷 / 偏热 / 偏湿）都出现过；
2. `31/78` 那张卡是**偏热**不是偏湿 —— 这一条专门验判定规则的**优先级顺序**；
3. 刷新页面之后**马上**有数据 —— 验的是**快照是 retained 的**。

第 3 条顺带暴露了仓库里两个世界的差别：`dashboard/` 订快照、快照 retained，
刷新立刻有；`web/`（M1 那版单节点页）订遥测、遥测虽然也 retained，
但它拿的是**报文**而不是 core 的结论。这一点在 D1 就会被看到。

### D2 —— 优先关注跟着数据自己换人

**目标**：三个宿舍都异常时，系统自己指出「先看哪个」，并且**随着数据自己换人**。

**思路**：`rank_priority()` 是四步排序，每一步只在「上一步打平」的那几个里比较：

```
1. 连续异常时长最长        → 赢家理由：「已连续偏热 8 分钟」
2. 时长相同，比这段的条数   → 赢家理由：「持续时间和 X 一样长，异常次数最多」
3. 条数也相同，比严重度权重 → 赢家理由：「偏湿比偏冷更要紧」
4. 全平，按 nodeId 字典序
```

三个设计要点：

- **只有进到某一步的节点才参与那一步的比较**。时长不同的那些，根本不该出现在
  比条数的名单里 —— 否则理由会写成一个没发生过的比较。
- **权重可覆盖**：改了权重，赢家和措辞一起变。
- **日志只在换人时打**。全程领先不重复打印（时长在涨不是新闻，换人才是）；
  判据比的是**节点 id** 而不是整句话 —— 整句话里嵌着越来越长的时长，
  拿它当判据会变成每一条都「变了」。

三套剧本（`d2_case1/2/3`）分别把「时长决出」「时长并列比条数」「时长条数全平比
严重度」各走一遍，**逐帧喂给 core 断言换人轨迹**，不用眼睛盯终端。

### D3 —— 事件闭环

**目标**：节点异常自动开案 → 人点一下「开始处理」→ **由后续数据自己判定好没好**。

**思路**：核心就是 3.5 那张状态机与那四条红线。三个额外的设计决定：

- **起点取报文里的 `time`，不取墙上时间**。剧本里 20:00 那一段要是按墙上时间记，
  会被记成「今天下午」，「持续了多久」这个业务问题的答案就没了。
- **在 `HANDLING` 上再点一次只是多记一笔动作**，验证窗口一次都不重置（理由见 3.5）。
- **core 重启把没结案的按未恢复收尾**，并在 `result` 里说明是重启造成的。

看板那个「开始处理」按钮接上这条链之后，**页面上按一下和 `send_cmd.py` 发一条
走的是同一条路** —— 这是「按钮不能直接把事件置成已恢复」这条红线在界面上的落点。

### D4 —— 三类故障的复现、定位与恢复

**目标**：故障能**造出来**、能**认出来**、能**修好**、修完能**验回来**。

**三类故障与各自的定位手段**：

| 故障 | 怎么制造 | 最直接的定位手段 | 修好之后怎么验 |
|---|---|---|---|
| ① 停掉 Broker | 终端里 Ctrl+C | 三个前端右上角翻成「未连接 / 重连中…」；core 打**一行** `[连接] 与 broker 断开：…`，**然后就再没有任何反应** | **两步**：重起 Broker；**再重启 core** |
| ② 写错 Topic | 少写一个字母，或把 `v1` 写成 `v2` | core 终端**什么也没有**；MQTTX 订 `dormmate/v1/#` 能看见这条孤零零的消息 —— **「发出去了但没人收」与「发都没发出去」就是这么分开的** | topic 改回约定值，重发，core 出现那一行 |
| ③ 发非法 JSON | `--raw` 发一段断掉的 JSON | core 终端 `[拒绝] …`（理由是 JSON 解析失败）；看板「被拒绝消息」面板多一行，**原文一字不差地摆出来** | 发一条合法报文，卡片照常更新 |

**故障 ① 的反直觉之处**（这是 D4 里最值得讲的一处）：四个进程里**只有 core 不会
自己重连**。

| 进程 | 断线后会不会自己回来 | 为什么 |
|---|---|---|
| 三个前端页面 | **会** | mqtt.js 自带重连（`reconnectPeriod: 2000`） |
| `simulator/simulator.py` | **会** | 用 `client.loop_start()`，内部是 `loop_forever()`，**那个函数里带自动重连** |
| **`core.py`** | **不会** | 主循环是 `while True: client.loop(timeout=0.5)`；`Client.loop()` 只处理网络事件，**paho 的自动重连只在 `loop_forever()` 里** |

于是停掉 Broker 再起回来，现场非常误导：**三个页面右上角自己回到「已连接」，
但节点卡片冻在最后一帧，一动不动。** 「页面已连接 + 数字不动」这个组合，
答案就是 core 没回来。这正是 D4 里那句「**不需要写自动修复**」的现场 ——
手动修复就是修复动作本身的一部分，不是漏做。

**另有一类不在三类里但更常见的：core 自己停了。** 判断方法**不是**「页面有没有
数据」（快照是 retained 的，core 死了页面照样有数据、而且长得一模一样），
而是页面顶部那条 **core 心跳提示**（超过 15 秒没有新帧就说「core 没声了」）。

为此 Phase9 补了两件事：

- **节点离线检测**：超过 `offlineTimeoutSec`（默认 30 秒）没收到遥测就
  `node.online = false`，快照里带上 `offlineSec` / `offlineText`（「已离线 3 分钟」）。
- **core 心跳**：系统再安静也每 `stateHeartbeatSec`（默认 5 秒）重发一帧快照，
  快照里写明 `staleAfterSec`（= 3 × 心跳）。于是「这一帧有多旧」这个判据
  **由 core 一家说了算**，三个前端一个阈值都不判。

### D5 —— 固定规则 + IsolationForest 轻量对照

**目标**：把「固定规则」和「模型」并排摆，看出两边在哪儿分岔。

**两条链，各干各的**：

| | 离线那条 | 在线那条 |
|---|---|---|
| 入口 | `analysis/ml.py`（或 `analysis.py` 顺带跑） | core 收到每条遥测 |
| 模型 | 一份历史 fit 出来的森林 | `models/<nodeId>.joblib`，**按宿舍各训一个** |
| 输出 | `report/ml_result.json` + 报告里的对照表 | `history.csv` 第 6 列 `ml_label`、第 10 列 `agree`，进快照 |
| 谁看 | 看板「ML 辅助判断」块、报告 | 看板「实时 Rule-ML 对照」表、报告「案例分析」 |

**四个设计决定**：

1. **判决统一用 `model.predict()`，不用 `score_samples()`、也不用 `offset_`。**
   sklearn 1.9.1 的 `IsolationForest.predict` 是拿 `decision_function < 0` 切的，
   跟 `model.offset_` 没关系 —— `contamination='auto'` 时 `offset_` 是 -0.5，
   照它写会写出和实际标签对不上的说明。实测在 `data/dorm-a_history_sim.csv` →
   `data/new_samples.csv` 上，`score_samples < 0` 与 `predict` 差 **1/6 行**。
   两套口径并存，两条 ML 链就会在同一行上给出不同结论。
2. **训练时一律跳过 `source=constructed` 的样本。** 不跳的话，构造样本的极端值会被
   当常态训进去，之后 ML 判它们「正常」，案例**静默地**复现不出来。判据**只有一处**：
   `train_iforest.is_constructed()` 查 `make_report.SOURCE_KINDS` ——
   一条判据自动覆盖 `构造 / 构造样本 / sample / samples / manual / constructed`，
   而 `sim / script / web` 这些**不**被跳过（模拟器和剧本是训练材料，构造样本不是）。
3. **三份词表各有各的家**（混用会静默出错）：

   | 位置 | 值 | 出处 |
   |---|---|---|
   | `predict()` 返回值 | `1` / `-1` | sklearn 内部 |
   | CSV 第 6 列 + 快照 `mlLabel` | `normal` / `abnormal` | `ml.ML_STATUS` |
   | 报告里展示 | 「接近历史常态 / 与历史明显不同」 | `ml.ml_text()` |
   | CSV 第 10 列 `agree` | `yes` / `no`，没判词时留空 | `history.AGREE_YES` / `AGREE_NO` |

   `agree` **不能写 Python 布尔** —— `history._cell()` 把 `bool` 当缺值打成空串
   （「温度是 True 没有意义」），写布尔进去这一列会整格消失，而
   「没判」和「判了不一致」在 CSV 里就长得一模一样了。
4. **边界不越**：不做 train/test 划分、**不算 accuracy / F1**、
   **不调参去刻意制造不一致**（`MODEL_PARAMS` 一个字都不改）。

`ml_judge.py` **放在项目根，不放在 `core/`** —— 因为 `core/` 是个 import 陷阱：
一旦里面出现 `__init__.py`，`import core` 就会静默指向那个目录，
几千行业务逻辑整段失效。有一条测试专门盯着 `core/` 下只许有 `config.json`。

### E1 —— 三间房并排的 3D 页面

**目标**：让「哪个空间需要关注」由画面自己说出来，而不是先点一下才知道。

**思路**：三个文件各管一段，切分线是「一间房」和「围着这一间房的东西」：

- `room.js` —— `buildRoom(prefix)`：这间房长什么样（地板 / 墙 / 床 / 窗 / 风扇 /
  标记环），加上「状态变了这间房自己怎么变」。**并排必须传 `prefix`**：
  不传的话三块地板全叫 `floor`，按名字找零件会随机撞上一个。
- `world.js` —— `createDormWorld`：三间房 + 一台会在房间之间飞的相机 +
  一个 CSS2D 标签层 + 拾取。
- `index.html` —— 只订 `dormmate/v1/state`，节点名单来自快照，点房间发 `focus`。

**三处硬设计**：

- **灯为什么不能跟着状态走**：单间房那边让整盏灯偏蓝就等于「这间房冷」；
  三间房各有各的状态时这招不成立 —— **一盏灯没法同时是三种颜色**。所以灯是固定的，
  状态只落在长在那间房自己身上的零件上（地板颜色、窗户开合、风扇转不转），
  这三样都跑不出那间房。
- **`NODE_MAP` 管的是「摆在哪儿」，不是「有哪些节点」**。哪几间要画由快照的
  `nodes[]` 说了算；这张表只说「如果来了 dorm-b，它摆中间」。
  节点名单写死一个就是一次假绿，测试盯着这件事。
- **点房间那一刻镜头不动**。发出去的就是一条 `focus`，镜头什么时候飞
  **由 core 发回来的下一帧说了算**。本地先挪过去看着「更跟手」，
  但那正是 E3 硬约束里点名的**伪造同步**。

### E2 —— 语音 + 拍照：多模态上「core 说了算」还成不成立

**目标**：人不想碰键盘的时候也能办事，而且办的结果**走同一条链、受同一条红线管**。

**思路**：分三层，每层只解决一件事。

- **core 新增 `snapshot` 指令** —— 第一条**碰得到案卷、但一个状态都不动**的动词。
  它让「说一句话」和「按一下按钮」在 core 那边变成同一类事件，可追溯、可审计。
- **`speakLine(snapshot, nodeId)` 收成纯函数**（在 `dashboard/logic.js` 里）——
  「这一句该念什么」只有一处实现，四个出口共用。要念的那句里
  **一个 `｜` 都没有**（那是给眼睛看的符号，念出来是「竖线」两个字），
  而且每次都句号收尾（要念出来得自成一句）。
- **`web/multimodal.js` 单独一个文件**，因为它要 `import` 那个 ES 模块，
  而 `web/script.js` **必须是**经典 script（测试用 `vm.runInThisContext` 整个跑它）。
  两边都改不了，于是中间架一层 `window.DormMateBridge`：
  `script.js` 提供取数据 / 发指令 / 拍照，`multimodal.js` 只管「什么时候拍、
  拍完怎么跟 core 对账」。**这让「拍照」只有一处实现**（画布、水印、字节数都在
  `script.js` 那边）—— 少一层的话，画布那段代码会被复制两份，两份迟早长得不一样。

### E3 —— 前端改成只订快照

**目标**：三个前端**只订阅 core 发布的 `dormmate/v1/state`**，只渲染、不做业务计算。

**改造前的缺口**：E3 之前**没有任何前端在读 `state`**，三个页面各订各的遥测 ——
也就是说业务判断有**三份实现**（core 一份、`dashboard/logic.js` 一份、
`web/` 认发布端一份）。E3 要的就是把这个收回来。

分三步：

| 步骤 | 做了什么 |
|---|---|
| **E3-1** | 快照扩展（补上事件列表、被拒绝消息两块前端要显示的东西）+ 抽出 `shared/config.js` |
| **E3-2** | 看板改成只订快照；`logic.js` 瘦成「读快照字段 + 把它们摆成人话」 |
| **E3-3** | 移动端跟进；跨端焦点（`focus`）打通 |

**两条硬约束靠测试而不是靠自觉**：

- `dashboard/logic.js` 的源码里**不许出现** `18` / `30` / `75` 这三个阈值、
  **不许出现**「偏冷 / 偏热 / 偏湿」这三个状态名、**不许出现**任何 `dorm-` 开头的
  节点名，也不许碰 DOM。节点名一律从快照里读。
- 三个前端点下去之后**屏幕上什么都不变**：点击只往 `dormmate/v1/cmd` 发一条指令，
  「处理中」要等 core 把新快照发回来才出现。有测试断言**拦下之后页面一个字节都没变**。

**E3 带来的一个真实代价**：core 没起的时候看板上一片空白（以前本地那本账还能自己走）。
这是有意的 —— 前端那本账和 core 那本账，开案时刻、结案判据、ID 形状都不一样，
同一段时间在屏幕上和在 `data/events.json` 里会是两个说法。**一本账胜过两本账。**

> ⚠ **一处必须主动说明的例外**：`web/` 是 M1 阶段的**单节点页**，
> 它仍然订遥测、并且自己引 `shared/rules.js` 调 `judgeStatus()` 算状态。
> 这不是「没改干净」，是**活化石** —— `README.md` 里明写了这两者「故意不一样」。
> 答辩时若被问到「前端到底认不认阈值」，要**主动把 `web/` 指出来**，

几个值得单独点出的用例：

- **「训练时不能把新数据一起 fit」**：把 `build_model` 换成探针跑一遍，
  断言交给它的那一帧**只有历史那 40 条**。为什么非得这么测：拿新数据一起 fit 的话，
  「正常」就被新数据自己重新定义了（一条离谱的读数顺手把正常范围拉大，
  于是它自己就不离谱了），而模型的 `estimators_` 个数、`n_features_in_`
  一个都不会变 —— **只看模型本身看不出这件事**。
- **`brokerUrl()` 不许写死端口**：把源码里那行 `const MQTT_WS_PORT = 9001;`

  `return 'ws://' + host + ':9001'` 这种写法照样绿 —— 而端口恰好就是那份配置
  最容易被抄错的地方。
- **`CMD_ACTION` 必须和 `events.py` 里的 `HANDLE` 是同一个词**：从 `events.py`
  源码里把那个字面量抠出来逐字比。写错一个字母就是一条「发出去没人认」的死指令，
  而 core 只会说一句「未知 action」。

### 5.3 D4 故障复现

**复现手册的位置**：`README.md` 的 `## Phase9 D4` 那一节，每一类都写了
「制造 → 现象 → 定位 → 手动修复 → 验证恢复」五步。

**一键发全九种坏消息**：`py -3.14 -m simulator.inject_faults`。它自己订
`dormmate/v1/log/reject`，跟「reject 上有几条」比的是 **topic + payload 全文**
和理由里的关键词 —— 所以「三条都在」和「三条都因为对的原因在」分得清。
**core 没在跑时那张表全红，它不会假装绿。**

九条覆盖：正常对照 / 非法 JSON / 缺字段 / topic 与报文对不上 / 未知节点 /
数值离谱 / 顶层不是对象 / topic 形状不对 / 清 retained 的空报文。

其中**第 5 条（99℃ / 200%）会被如实收下并判成偏热** —— 这一条不是「故障被拦住」，
而是用来证明 **core 里没有任何范围校验**（见 6.2）。九条里**必须有一条确定能通过的
当对照**：全都能拦住也可能是「什么都拦」。

**复现故障时不用真的搞坏正在演示的系统**：把 `core/config.json` 里 `broker.port`
改成别的口，用 `--config <那份副本>` 起一个隔离的 core，再起一个听那个口的 Broker，
杀掉 Broker 等 25 秒 —— 那个 core 的日志里**既没有「已连接」，也没有任何重连失败
的记录**，`netstat` 上那个口只有 `LISTENING`、没有 `ESTABLISHED`。

**还有一类不在三类里但更常见：core 自己停了。** 判断方法不是看页面有没有数据
（快照 retained，core 死了页面照样有数据），而是看页面顶部那条 **core 心跳提示**。

**「落在门槛的另一侧」，不是「这条读数离谱」**。11:25 那条分数 -0.0564 刚过线，
一半是数据、一半是这个门槛。要更严格就把 `contamination` 写成一个具体比例，

## 六、自主设计决策表、已知限制、开放拓展

### 6.1 自主设计决策表

下面这些**不是题目要求，是自己定的**。每条都写清「定了什么」和「为什么」。

| # | 决策 | 备选 | 为什么选它 |
|---|---|---|---|
| 1 | **判断只在 core**，三个新前端一条阈值都不认识 | 各页面自己算，或共享一份规则 JS | 判断一旦有两份实现，同一个宿舍在同一时刻可能有两个说法，而且**不报错**。收回 core 之后，规则只有一处；前端那份连 `18/30/75` 这三个数都不许出现（有测试盯着） |
| 2 | **状态判定顺序不可调换**（先偏冷，再偏热，再偏湿） | 按「哪个更严重」排 | 顺序决定了边界上的归属：31℃/80% 两条线都越了，规则 2 先命中所以是**偏热**。定死顺序才有唯一答案，而不是「看情况」 |
| 3 | **恢复只能由后续数据判**（红线），`handle` 只推到 `HANDLING` | 按钮直接把事件置为已恢复 | 按钮说「我处理了」和事实说「它好了」是两件事。这条不靠自觉，靠**结构上做不到**：`handle_command` 拿不到节点状态 |
| 4 | 事件判据用**运行期计数**，不数存档条数 | 看 `verify` 数组最后 N 条 | 存档上限和判定门槛是两个独立配置，前者小于后者时，判据永远凑不齐，而且**连线索都没有**（`verify_dropped` 一直是 0） |
| 5 | `verify_from` 记**下标**，重复点击不重置窗口 | 每次点击重置验证窗口 | 重置的话连点几下就能把「连续 M 条依旧异常」一直往后推，事件永远判不出未恢复，验证环节白设 |
| 6 | **`cmd` 与 `log/reject` 都不 retained** | 全部 retained，图省事 | 指令 retained 会让下次起 core 时**凭空**把某条事件推进「处理中」；坏消息 retained 会让每开一个看板都先看到它 |
| 7 | **topic 只有 `config.py` 一处出处**；`config.js` 双向核对 | 前后端各写一份常量 | 两处各写一份时，改 topic 只改一边，**两边都不报错**，只是页面上永远没有数据。这个坑在旧三段式 topic 迁移里踩过一次 |
| 8 | CSV 新列**只在末尾追加** | 插在语义相关的列旁边 | 文件头承诺过「人拿 Excel 打开时看的是位置」。追加在末尾是唯一不移动前九列的选择 |
| 9 | `agree` 落**字符串** `yes`/`no`，不落布尔 | 落 Python `bool` | `_cell()` 把 `bool` 当缺值打成空串，写布尔进去这一列会**整格消失** —— 而「没判」和「判了不一致」在 CSV 里就长得一模一样了 |
| 10 | 训练**跳过** `source=constructed`，判据只有一处 | 让训练脚本各自判断 | 不跳的话极端值被当常态训进去，案例**静默地**复现不出来。判据收在 `SOURCE_KINDS` 一处，一条覆盖六种写法 |
| 11 | 两条 ML 链**统一用 `predict()`** | 用 `score_samples()` 或 `offset_` | 实测两者差 1/6 行。两套口径并存，两条链会在同一行上给出不同结论 |
| 12 | 快照**只加字段、不升版本**（`v` 仍为 2） | 每次加字段就升版本 | 加字段本身向后兼容；只有「前端订阅/解析方式变了」才需要升版本。这次前端仍然只订一条 state，订阅模型没变 |
| 13 | 三间房的**灯固定**，状态只落在房间自己的零件上 | 灯跟着状态变色 | 一盏灯没法同时是三种颜色。状态落在跑不出那间房的零件上（地板 / 窗 / 风扇），一眼分得清是哪一间 |
| 14 | `NODE_MAP` 只说**「摆在哪儿」**，不说「有哪些节点」 | 拿它当节点名单 | 哪几间要画由快照的 `nodes[]` 说了算；写死名单就是一次假绿，测试盯着 |
| 15 | 三个前端**点了之后屏幕不变**，等 core 的快照 | 本地先改，看着跟手 | 本地先改就是 E3 点名的**伪造同步**。代价是「过一拍才变」，所以按钮下面那行说明是必须的 —— 它回答「指令发给 core 没有」 |
| 16 | 看板给**一句**、报告给**完整的一笔** | 两边都摆完整表格 | 看板是**扫一眼**的地方，报告是要坐下来看的。同一个结论，两种粒度各有各的用处 |
| 17 | 报告**是数据的纯函数**，且不进库 | 手工润色后入库 | 「报告结果禁止手工修改」的前提就是「报告是跑出来的」。一旦入库，看到的人第一反应是去改文件，而不是改输入再重跑 |
| 18 | 事件**完整记录在 `events.json`**，快照只留最近 20 条 | 快照里放全量 | 快照是「一帧」，是给前端画表格用的；档案是另一回事。两个数混成一个，环形缓冲一满，看板上「共 N 条」会跟着数组一起封顶 |
| 19 | 假 mqtt 桩**不校验** `publish` 的调用形状 | 给桩加签名检查 | 补了也还是桩 —— 「真 mqtt.js 收不收这个形状」测试全绿也说明不了，只能拿真页面验一次。**这条限制写进文档，不假装覆盖了** |
| 20 | 已恢复 / 未恢复**照印英文原值** `RECOVERED` / `UNRESOLVED` | 另起一套中文说法 | 对着一份文件和一个终端截图时，不用在两套叫法之间换算 |

### 6.2 已知限制

**分三类，共 60 多条，完整清单在 `README.md` 的 `## 已知限制` 那一节。**
这里给最需要提前知道的。

#### （1）设计如此（当前步骤就有意不做）

| 限制 | 原因 |
|---|---|
| **报文没有乱序保护** | `latest` 一律被**最后收到**的那条顶掉，比的是到达顺序而不是 `time`。重发一条旧数据，卡片上读数会退回去、持续时长会缩到 0。真正的防线是剧本里同节点时间必须递增（有测试守着） |
| **core 不做范围校验**，99℃ / 200% 会被如实收下 | 九道判据管的是「这是不是我们要的那种数据」（形状 / 类型 / 来路），不管这个数在物理上合不合理。要拦得先定下「合理范围」是哪个范围、超了算拒收还是打标 —— 那是另一套需求 |
| **`data/history.csv` 会一直长**，没有轮转、没有上限 | 它是**档案**，一条都不许丢。`--all-nodes` 默认 5 秒一轮 = 每小时 2160 行，跑一整天约 5 万行、两三 MB。要归档就在演示前把文件挪走 |
| **core 一启动就会收到 retained 的最后一条读数**，把它当成当前数据 | `RETAIN=True` 是为了「后开的看板立刻看到数值」，代价是 core 也照收 —— 它在协议上分不出这条是三小时前的还是刚发的。所以跑剧本前要先清 retained |
| **清 retained 不会清掉 core 的内存** | 空报文只记一笔，**不动节点**：已经在跑着的 core 里，那个节点的历史、开着的那一段、离线计时都照旧 |
| **「处理中」是事件的状态，不是节点的状态** | 节点那边只有「这一段现在是不是异常」。两套混成一套，「处理中」会被当成一种环境状况去和「偏湿」比严重度 |
| 点多少次「开始处理」都**不改结局** | 连点 N 次只是多记 N 笔动作，验证窗口一次都不重置 |
| 规则有**两份实现**（Python / JS），必须手工同步 | 没有自动同步机制。不同步的后果是报告顶部出现红色横幅。`miniapp/utils/rules.js` 那份由 8211 组交叉比对盯着 |
| `web/` 与 `dashboard/` 对 `status` 的态度是**两个世界** | `web/` 以发布端发来的 `status` 为准；`dashboard/` 连阈值都不认识。看数据时得知道自己在哪个页面上 |
| 摄像头只保留最后一张快照；语音指令是**字面包含**匹配 | 说「拍照」才行，说「拍张照」不算。识别引擎会带出标点和语气词，所以不能整句相等，但也没做同义词表 |
| `mobile/` 上没有趋势图、事件表、3D、语音 | 那是**信息分工**不是漏做：手机的角色是「人在宿舍里随手看一眼」 |
| 3D 场景的状态切换是**瞬间到位**的，不做缓动 | 按钮点下去要立刻看到变化，立刻到位让「打开了吗」「转了吗」一眼可验、也好写测试 |

#### （2）还没做

| 限制 | 卡在哪 |
|---|---|
| **core 断线之后不会自己重连** | 主循环是轮询式的 `while True: client.loop(timeout=0.5)`，而 paho 的自动重连只在 `loop_forever()` 里。**手动修复 = 把 core 那个终端 Ctrl+C 再起一遍**（D4 明确不要求自动修复）。要接上就是主循环里 `client.loop()` 返回非 0 时调一次 `client.reconnect()`，约 6 行 —— `on_connect` 那边早就为它写好了重新订阅的逻辑 |
| **没有后端、没有数据库** | 纯静态前端 + 本机 Broker，数据不落库，页面关掉就没了 |
| **前端测试不覆盖浏览器真实行为** | 测试是 Node + 一个最小 DOM shim 跑真实的 `script.js`，摄像头 / 麦克风 / Canvas 都是桩。**能证明逻辑对，不能替代真机验证** |
| 同一份 `--all-nodes` 起两次会互相顶下线 | 三个节点共用一根连接，`client_id` 是固定的；Broker 会按 client_id 把先来的踢掉 |
| 看板 ML 那一段读不到时**没有重试按钮** | 只能刷新页面才会再读一次（原因原样写在页面上：`HTTP 404` 和 `Failed to fetch` 指向不同的排查方向） |
| 3D 视图的动画循环一直在跑 | 风扇不转时也在重绘。看板本来就是常驻页面，开销可接受；真要省就在风扇停下时停掉循环 |

#### （3）环境依赖（不是 bug，但很容易被当成坏了）

| 限制 | 说明 |
|---|---|
| 摄像头和语音识别**要求安全上下文** | 只在 `https` 或 `localhost` 下可用。手机用 `http://<IP>:8000/` 打开时 `navigator.mediaDevices` 直接是 `undefined` |
| Chrome 的语音识别**要求联网** | 它是把录音传到服务器上识别的，不是本地识别。断网 / 走代理会报 `network` |
| Firefox 没有语音识别接口 | 页面会明确提示换 Chrome / Edge |
| `analysis/ml.py` 需要 scikit-learn | 没装时**不甩 traceback**，打印一句「没装 scikit-learn」并给出安装命令就退出；报表、摘要、看图三件事一件都不受影响 |
| `report/ml_result.json` 记的是**上一次跑的时刻**，不是实时的 | 它是快照，跟 MQTT 那条实时链无关。页面上必须写着这层意思（`#ml-note` 那句），删掉那句话，看的人就会把结论安到刚收到的温湿度上 |
| 对照表里的分数**绑 scikit-learn 版本** | 上面那张表的六个分数是 `scikit-learn 1.9.1 + random_state=42` 跑出来的，换版本可能就变。测试里那几条会红，红的正是「文档这张表过期了」——照着新分数把表和测试一起更新，**别改参数去迁就旧数字** |
| Python 必须用 **64 位**的 `py -3.14` | pandas / matplotlib 没有 32 位 Windows 包，用 32 位 `python` 装会报「找不到编译器」，很容易误判成缺 VS 构建工具 |

### 6.3 开放拓展

按「改动的收益 / 代价」排，前三条是投入产出比最高的。

| # | 拓展 | 具体怎么做 | 为什么值得做 |
|---|---|---|---|
| 1 | **core 自动重连** | 主循环里 `client.loop(timeout=0.5)` 返回非 0 时调一次 `client.reconnect()`，约 6 行 | 这是目前**唯一一处「用户必须手动干预系统才能恢复」**的地方，而且现场表现极具误导性（页面显示「已连接」但数字不动）。`on_connect` 里重新订阅的逻辑**早就写好了**，就等这一行接上 |
| 2 | **报文乱序保护** | 给每个节点加一条闸：「`time` 不比 `latest` 新就只进历史，不顶掉当前值」 | 补上已知限制里最实际的一条。代价是要先定清楚「同一条报文重发」算不算乱序 |
| 3 | **`data/history.csv` 轮转 / 归档** | 按天切分，或超过 N 行时归档到 `data/archive/` | 档案会一直长。注意**不能简单地删旧行** —— 它是「一条都不许丢」的档案，正确做法是切分而不是丢弃 |
| 4 | **ML 门槛改成显式比例** | `contamination` 从一个具体比例取，而不是 `'auto'` | 「与历史明显不同」现在门槛偏松（回看自己的训练集也有 18/40 被判不同）。改成显式比例之后，那句话才真的能读成「这条不合理」。代价是失去「不需要预设异常比例」这个优点 —— 这一条是**取舍**，不是纯粹的改进 |
| 5 | **把断言桩换成真的 `mqtt.js`** | 用一个真实的 WebSocket Broker 跑一次前端集成测试 | 假桩不校验 `publish` 的调用形状，所以「真 mqtt.js 收不收」这件事目前无覆盖。这不是能靠加断言补上的（补了也还是桩） |
| 6 | **报告的趋势图做成可交互** | 把内嵌 PNG 换成自绘 SVG 或 canvas，加十字准星与 tooltip | 现在是死图，要看数字得看图下面那张表。代价是报告不再是「单文件、零依赖」—— **这个取舍必须先想清楚**，单文件是这个报告最重要的性质之一 |
| 7 | **`mobile/` 补上事件表** | 数据本来就在同一份快照里，加 DOM 即可 | 但要先回答「手机和看板的分工还剩什么」—— 看板那块大屏幕的意义正是「坐下来看」，两边功能对齐之后这个分工就没了 |
| 8 | **多节点模型按节点各训各的之外，再加一层全局基线** | 每个节点一个模型 + 一个跨节点共享的「宿舍通用」模型 | 现在 `dorm-b` / `dorm-c` 样本少时模型质量差。全局基线可以做冷启动，也可以用来解释「为什么同一个读数在不同宿舍判得不一样」 |
