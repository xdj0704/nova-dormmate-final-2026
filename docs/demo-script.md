# DormMate 演示视频脚本（约 7 分钟）

> **用途**：答辩 / 提交用的演示视频。一段一段拍，每段独立可重来。
>
> **读法**：「旁白」那一栏是**要念出来的话**，`【】` 里的是**动作提示**，不用念。
> 旁白里的数字都是能复现的 —— 每段用哪份剧本、按哪个按钮，都写在「屏幕画面」里。
>
> **时间分配**：8 段，合计 7 分 00 秒。每段都留了 5 秒左右的余量，念快了不至于短。

| 段 | 内容 | 起止 | 时长 |
|---|---|---|---|
| 1 | 开场：这是个什么系统 | 0:00 – 0:40 | 40″ |
| 2 | D1：一条消息，三个界面同时动 | 0:40 – 1:30 | 50″ |
| 3 | D2：系统自己指出先看哪一间 | 1:30 – 2:20 | 50″ |
| 4 | E2：用说的 | 2:20 – 3:20 | 60″ |
| 5 | D3 / E1 / E3：处理、同步、数据自己判恢复 | 3:20 – 4:40 | 80″ |
| 6 | D4：把 Broker 停掉 | 4:40 – 5:50 | 70″ |
| 7 | D5：规则说正常，模型说不像 | 5:50 – 6:30 | 40″ |
| 8 | 收尾：亮点与局限 | 6:30 – 7:00 | 30″ |

## 拍摄前（不录，一次性）

### 要起来的进程

```
1. start_broker.bat                                  # Mosquitto：TCP 1883 + WebSocket 9001
2. py -3.14 core.py                                  # 终端 1 —— 整段录制期间不要关
3. start_web.bat                                     # 静态服务器 8000，顺便打开 web/ 页
```

浏览器开四个标签，都留在那儿随时切：

```
http://localhost:8000/dashboard/     看板（三张卡 + 当前重点 + 事件表）
http://localhost:8000/three/         3D（三间房并排）
http://localhost:8000/mobile/        移动端（谁该管 / 点一下看他 / 开始处理）
http://localhost:8000/web/           M1 那版单节点页 —— 第 4 段的语音在这个页面上
```

### 三个必须避开的坑

| 坑 | 后果 | 怎么做 |
|---|---|---|
| **没清 retained** | core 一启动就先收到一条几小时前的旧读数，当场被当成"当前数据" | 开录前先往三个 topic 各发一条空 payload 清掉 |
| **跑剧本时模拟器还在发** | 剧本的判据是"**连续**几条"，中间插进任何一条别的读数都会把计数打断 —— 结果是"事件没按剧本结案"，看上去像 core 坏了 | 跑任何剧本之前，先停掉 `--all-nodes` 那个模拟器 |
| **把 `report/report.html` 拍进画面** | 那份**还是占位内容**，不是真报告 | 要拍的是 **`report/history-report.html`** |

### 浏览器两点

- 用 **Chrome 或 Edge**，别用 Firefox —— 它没有语音识别接口。
- **第 4 段必须在电脑前、在 `http://localhost:8000/` 上拍**，不能在手机上用
  `http://<IP>:8000/`。麦克风和摄像头要求**安全上下文**，走 IP 打开时
  `navigator.mediaDevices` 直接是 `undefined`，语音直接就废了。
  （手机端本身有它自己的戏份，在第 5 段。）

## 第 1 段 · 开场：这是个什么系统

**时间** 0:00 – 0:40（40 秒）
**屏幕** `dashboard/` 全屏。三种状态各占一张卡（先别跑剧本，就用当前画面）。

> **旁白**
>
> 这是 DormMate，一个多节点宿舍环境助手。
>
> 三间宿舍，每间一个温湿度节点。数据走 MQTT 上来，经过中间一个 core 算出结论，
> 再推给看板、手机和 3D 三个界面。
>
> 整个系统只有四个进程和一个消息代理 —— 没有服务器程序，也没有数据库。
>
> 它要回答的其实只有一个问题：**现在该先管哪一间；管完之后，到底好没好。**

**【动作】** 鼠标在"当前重点"那一行上停一下，再划到下面三张卡。
**不要**在这里逐个介绍模块，一句话带过就行 —— 后面每一段都在用。

## 第 2 段 · D1：一条消息，三个界面同时动

**时间** 0:40 – 1:30（50 秒）
**屏幕** 分屏：左边终端，右边 dashboard；第二屏再带出 mobile 和 3D。

**【动作】** 在终端里跑：

```
py -3.14 -m simulator.simulator --script simulator/scenarios/phase1_demo.json
```

> **旁白**
>
> 我发一条消息出去。
>
> dorm-a，二十五度、湿度六十 —— 正常。
> dorm-b，三十一度、湿度七十八 —— 偏热。
> dorm-c，十六度 —— 偏冷。
>
> 留意 dorm-b 这一条。它的湿度七十**八**，也过了七十五那条线，但状态给的是
> **偏热**，不是偏湿。因为判定是**有顺序**的：先看温度低于十八算偏冷，
> 再看温度到了三十算偏热，最后才轮到湿度。顺序一换，这一条就变成偏湿了 ——
> 所以这个顺序不能动。
>
> 再看这个。【切到三个界面】一条消息发出去，手机端和 3D 页面同时跟着变了。
>
> 它们没有各算一遍。三个界面订阅的是**同一条** core 发出来的快照 ——
> 谁该是什么状态，是 core 算好的。

## 第 3 段 · D2：系统自己指出先看哪一间

**时间** 1:30 – 2:20（50 秒）
**屏幕** dashboard 顶部「当前重点」；切到 3D，那一间房上有脉冲光环。

**【动作】** 停掉模拟器，跑：

```
py -3.14 -m simulator.simulator --script simulator/scenarios/d2_case1.json
```

> **旁白**
>
> 现在 dorm-b 和 dorm-c 同时出问题了。系统自己挑了一间，还给了一句话：
>
> 「已连续偏热…分钟，异常次数最多」。
>
> 这句话不是套模板写死的。它是**真的比出来的** —— 比四步：先比谁这一段异常
> 持续得久；一样久，就比这段里攒了多少条；条数还一样，就比哪个状态更要紧；
> 全平了，才按名字排。赢在哪一步，它就说哪一步 —— 赢在时长的那条不会去提异常次数。
>
> 还有一点要注意。【指到 20:07 那一段】这会儿 dorm-b 的读数**已经回到正常**了，
> 可是"当前重点"还是它。
>
> 这不是页面没刷新 —— 是**那一段还没结束**。要**连着三条**正常读数，
> 这一段才算真的过去。数据说结束，才算结束。

## 第 4 段 · E2：用说的

**时间** 2:20 – 3:20（60 秒）
**屏幕** 切到 `web/` 页面（M1 那版单节点页 —— 语音落在这个页面上）。允许麦克风。

> **旁白**
>
> 有时候手上有事，碰不了键盘。
>
> 【点「语音指令」，说】「查看 dorm-c」—— 手机端和 3D 一起切到了 dorm-c。
>
> 这里有个细节值得说：页面回我的话是"**已发出**"，不是"焦点已经切过去了"。
> 因为它只知道消息交给了 broker —— core 收没收到、认不认这条指令，
> 要等**下一帧快照**回来才算数。它不替 core 宣布结果。
>
> 【说】「朗读」—— 它把这间现在的情况念出来。念的是完整的一句话，
> 不是照着表格一行一行读。
>
> 【说】「记录现场」—— 拍一张。
>
> 【指照片水印那行】照片上这行字是：**宿舍名、事件编号、时间**。
> 它挂到 dorm-c 此刻**未结案**的那条事件上，不是随便存一张图进文件夹。
>
> 要是这会儿没有未结案的事件，页面会直说，core 那边也会拒收 ——
> 它**不会编一个编号出来**。事后有人拿一个假编号去案卷里查，查不到才最坏。

## 第 5 段 · D3 / E1 / E3：处理、同步、数据自己判恢复

**时间** 3:20 – 4:40（80 秒）
**屏幕** 三块并排：手机端 / dashboard / 3D。这一段是全场重点，画面要给足。

**【动作】** 停掉上一个模拟器，跑：

```
py -3.14 -m simulator.simulator --script simulator/scenarios/d3_event.json
```

> **旁白**
>
> dorm-b 偏热。值班的人在手机上按一下「开始处理」。
>
> 【按下去】三块界面同时变了：手机上的按钮翻成处理中；看板事件表那一条
> 从"待处理"变成"处理中"；3D 里 dorm-b 这间房的顶上，挂出一个小小的"处理中"。
>
> **但是——事件本身没有变成"已恢复"。**
>
> 按一下按钮，只够把它推到"处理中"。这是这个项目的一条硬规矩。
> 不是靠我记得别这么写 —— 是**代码结构上就做不到**：处理指令那个函数的函数体里，
> 一次都没有出现过节点状态。它拿不到，也就改不了。
>
> 接下来才是关键。【等剧本继续跑】我继续发数据：二十九度、二十七度、二十五度 ——
> 连着三条正常。
>
> 第三条进来的那一刻，事件**自己**翻成了「已恢复」。恢复时间取的是
> **这条报文里写的那个时间**，不是我按按钮的时间。
>
> 【指 3D】这间房也变了：地板从红色回到灰色，风扇停下来。
>
> 【切到报告】这份复盘在报告里 —— 注意，不是 report.html 那一份，
> 是 **history-report.html**。事件时间线上写得很清楚：什么时候开案、谁处理的、
> 处理之后收到了几条、什么时候结的案。
>
> 剧本的第二幕是**对照**：dorm-c 处理之后数据还是偏湿，连着三条异常 ——
> 事件最后判的是「未恢复」。没有这一幕，"按了就能好"和"数据说的才算"，
> 在截图上根本分不出来。

## 第 6 段 · D4：把 Broker 停掉

**时间** 4:40 – 5:50（70 秒）
**屏幕** 终端为主，右侧 dashboard 一直可见。别切走。

**【动作】** 到 Broker 那个终端按 Ctrl+C。

> **旁白**
>
> 现在演示一次故障。我把 Broker 停掉。
>
> 【指三个页面】三个页面右上角立刻变成"未连接、重连中"。
> core 那边打了一行"与 broker 断开"—— 然后，**就再也没有任何反应了**。
>
> 【重启 Broker】我把 Broker 起回来。
>
> 页面自己回到"已连接"了。
>
> **但是数字不动了。** 看板上的温湿度还是刚才那一帧。
>
> 这里最容易被骗：页面说已连接，看着一切正常，可数据是**冻住**的。
>
> 【指页面顶部那条 core 心跳】怎么定位？看这一条 —— 它已经十几秒没更新了。
> 说明 core 没回来。
>
> 为什么？四个进程里**只有 core 不会自己重连**。三个页面用的是 mqtt.js
> 自带的重连，模拟器走的是 loop_forever —— 那个函数里带自动重连。
> core 用的是轮询式的 loop，而 paho 的自动重连**只在 loop_forever 里面**。
> 所以它断了就是断了。
>
> 【重启 core】把 core 重启一遍 —— 数据立刻就跟上来了。
>
> 这次演示里，"手动修复"不是一个偷懒的省略，它**就是修复动作本身**。
> 接自动重连大概只要六行，我把它写在文档的拓展里了。

## 第 7 段 · D5：规则说正常，模型说不像

**时间** 5:50 – 6:30（40 秒）
**屏幕** 浏览器打开 `report/history-report.html`，滚到「Rule-ML 对比」和
「案例分析：规则和 ML 为什么不一样」两块。

> **旁白**
>
> 这份报告里有一块对照。
>
> 固定规则回答的是"**越没越线**"—— 三条提前写好的线：温度低于十八、温度到三十、
> 湿度到七十五。
>
> 模型回答的是另一个问题："**这条读数像不像这间宿舍平时那些**"。
>
> 这两个问题本来就不必给出同一个答案，不一致也不说明谁错了。
>
> 这一份数据里，有判词的八十多行，**三十二行**两边不一样。
> 我把**两个方向**都列出来了：规则说正常、模型说不像的，八行；
> 反过来，规则说异常、模型说像的，二十四行。
> 只留一个方向的话，另一个方向在表里看着和"两边都同意"长得一模一样。
>
> 【指最后一列】看这一列 —— 这间宿舍历史上温湿度的范围。
> 比如这一条，dorm-b，二十三度、湿度三十二 —— 规则判正常；
> 可 dorm-b 平时湿度从来没到过这么低的位置，所以模型说不像。
> 对着这一列看，**为什么不一样就有答案了**，不用猜。

> ⚠ **拍摄提示**：这一段的数字（八十多行 / 三十二行 / 八行 / 二十四行）是
> **从当前那份 `data/history.csv` 现算出来的**。你录制前要是又灌过数据，
> 重新生成一遍报告，然后**照着屏幕上真实的数字念**，别照着这本脚本念。
> 报告里每个数都是算出来的，脚本里这几个数只是"此刻长什么样"的快照。

## 第 8 段 · 收尾：亮点与局限

**时间** 6:30 – 7:00（30 秒）
**屏幕** 回到 dashboard 全景，鼠标慢慢划过三张卡。

> **旁白**
>
> 最后说三件事。
>
> 第一，这个系统里**判断只有一处**。三个界面一条阈值都不认识，
> 它们只把 core 算好的结论画出来。这条有测试盯着 —— 前端那个文件里
> 一旦出现十八、三十、七十五这三个数，测试就红。
>
> 第二，**恢复不由按钮决定**。按钮说"我处理了"，数据说"它好了"，
> 这是两句话，得由后一句话说了算。
>
> 第三，局限我也写在文档里，不藏着：core 断了不会自己重连；
> core 也不做数值范围校验 —— 九十九度它照收。它管的是
> "这是不是我们要的那种数据"，不管这个数在物理上合不合理。
>
> 七分钟到这儿。谢谢。

## 录制注意事项

| 事 | 说明 |
|---|---|
| **重录某一段的代价** | 每段都能独立重录，但**第 3、5 段跑过剧本之后要清 retained 再重录**，否则残留的读数会打乱"连续 N 条"的计数 |
| **第 6 段最难重录** | 它要真的把 Broker 停掉再起来。安排在所有其他段落都拍完之后再拍这一段 |
| **第 5 段一次过** | `d3_event.json` 的 interval 是 1 秒、15 帧 ≈ 15 秒跑完，"连着三条正常"那一瞬很快。念旁白时要**提前**说到"接下来才是关键"，别等画面已经变绿了才开口 |
| **节点掉线** | 任何一段中断超过 **30 秒**，节点会被判成离线、不再参与排序。念旁白卡壳超过 30 秒就重录这一段 |
| **别拍的东西** | `report/report.html`（占位）、`data/ml_note.txt`（占位）、`broker/` 那个目录（未跟踪的副本） |
| **两份 ML 不是一回事** | 第 7 段那份报告走的是**离线链**（`analysis/ml.py`）。看板上还有一块「实时 Rule-ML 对照」，那是**在线链**（core 自己判的），两边的数据源和口径不同，别在同一个镜头里混着讲 |

## 与原始流程的三处出入（照实写，别照原流程念）

| 原始流程写的是 | 实际是这样 | 脚本里怎么处理的 |
|---|---|---|
| 5. "移动端执行**开启风扇**处理动作" | 移动端**只有一个按钮：「开始处理」**。它没有"开风扇"这个动作 —— 三个指令动作是 `handle` / `focus` / `snapshot`，跟风扇无关。3D 里那台风扇会转，是因为**房间偏热**（环境）或者**事件处理中**（事件），是状态的**结果**，不是能按的按钮 | 第 5 段把它念成"值班的人按开始处理"，风扇转当作画面结果来说，**不说"点了风扇"** |
| 4. 语音交互 | 语音**只在 `web/` 那版单节点页上**（`web/multimodal.js`）。看板那个「语音提醒」按钮**只能朗读、没有麦克风**。而且麦克风要求安全上下文，手机上用 IP 打开是直接不可用的 | 第 4 段明确在 `web/`、在 `localhost` 上拍，并说明了为什么不能挪到手机 |
| 6. "重启 Broker 修复，验证恢复" | **重启 Broker 只能修好一半**：三个页面会自己重连回"已连接"，但 core 不会 —— 数据冻住。必须**再重启 core** | 第 6 段把这个拆成**两幕**来演。这正是 D4 最值得讲的地方，按原流程念反而会把系统讲错 |

另外补一处：原始流程第 5 段的顺序是"移动端处理 → 多端同步 → 收到新数据判恢复 → 报告"。脚本保持了这个顺序，但在中间插了一句"事件没有变成已恢复"——这是全场最容易被忽略、也最能体现设计意图的一拍。
